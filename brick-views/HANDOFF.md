- 2026-09-09 (dashboard scalability): Admin aggregation moved out of JavaScript and into Postgres. Both list endpoints were doing `select().from(sessions)` with **no WHERE** and grouping in JS — shipping every session ever recorded across the Atlantic on each dashboard load. Invisible at 2 rows, unusable after a few cohorts.
  - **Measured first, not guessed.** Baseline `SELECT 1` against Neon (us-east-1, from India) is **253ms** — that round trip is the floor under every request, and it is most of what a "fast" endpoint costs. The seconds-long "Loading…" seen locally is `vercel dev` recompiling each function per request, which does not exist in production.
  - **Load-tested at 200 students** (2,000 sessions, 6,000 attempts, 500 hints, seeded and then fully removed): `/api/admin/puzzles` went **240ms → 250ms** — flat against a ~1000× increase in history. `/api/admin/participants` went **250ms → 485ms**, and that rise is response *size* (2 rows → 202), not scanning: it now scales with the number of participants displayed rather than with the amount of history behind them. Aggregates were verified exactly against a hand count for a sampled student (attempted/solved/total time/hints all matched).
  - **Fan-out is the trap these queries avoid.** Joining sessions to hint_usages in one pass would count a session once per hint, inflating `puzzlesAttempted`. Hints are therefore a separate subquery joined back per participant, and the puzzle report collapses attempts to a per-session count in a CTE before aggregating by puzzle.
  - **Medians moved to `percentile_cont(0.5) WITHIN GROUP … FILTER (WHERE is_solved)`**, which interpolates between the two middle values exactly as the old JS median did. Still medians, not means: one child who wanders off mid-puzzle would drag an average badly at class size.
  - **Added `sessions_puzzle_id_idx`.** `sessions` was indexed on `participant_id` only, so grouping by `puzzle_id` meant a sequential scan of the whole table on every dashboard load.
  - **Note for future load tests:** the synthetic generator correlated puzzle assignment with solved status (both derived from `pi + si`, and 21 puzzles shares a factor with the mod-3 solved rule), so some puzzles came out with 0 synthetic solves. That is an artefact of the generator, not the aggregation — use independent random sources next time.
  - **Not done:** `api/admin/participant.ts` (the single-participant drill-down) still fetches that one child's rows and merges in JS. That is bounded by one participant's history, so it is fine now, but it will want the same treatment if a child ever accumulates thousands of attempts.

- 2026-09-09 (admin v2): Puzzle-side admin — stats, per-puzzle timers, colour mode, and a live catalogue.
